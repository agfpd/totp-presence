# totp-presence

> Как агент может знать, что он говорит со своим владельцем — а не с
> текстом, который его имитирует.

**Платформы:** macOS, Linux, Windows через WSL.

## Проблема: идентичность в текстовых каналах

На чём агент основывает уверенность, что сообщение «это я, сделай X»
действительно пришло от владельца?

На практике — через **канал**: привязанный Telegram-аккаунт, терминал,
IDE-окно, email с доверенного адреса. Но ни один из этих сигналов не
говорит про человека. Они говорят про канал — и принимают на веру, что
за каналом сидит именно владелец:

```
агент --[проверяемо]--> канал --[на веру]--> человек
```

Агент может проверить первое звено: «канал тот самый». Второе —
«правильный ли человек за каналом» — проверить нечем: в тексте этой
информации нет. Это не недоработка, а свойство текстового канала, и
оно не лечится более способной моделью.

Три разных атаки — одна корневая дыра:

- **Угон Telegram** → идентификатор чата тот же, агент продолжает
  слушаться.
- **Физический доступ к машине** → открытый терминал = полный контроль.
- **Prompt injection** → вредоносный текст в документе утверждает, что
  его написал владелец, и агент не может это опровергнуть.

Во всех случаях агент доверяет каналу, потому что другого основания
у него нет.

## Решение

`totp-presence` добавляет второй, независимый канал проверки —
секретный ключ, который живёт **вне** канала связи: в аутентификаторе
на телефоне владельца (Google Authenticator, Apple Passwords, 1Password,
Authy и т.п.).

```
агент --[проверяемо]--> TOTP-сигнал --> физический человек
```

Ключевое свойство: **инъекция не знает секретный ключ** — а значит,
не может сгенерировать валидный код, не может открыть сессию и не
может дотянуться до защищённых действий.

### Как это выглядит на практике

1. Владелец открывает аутентификатор на телефоне и видит 6-значный
   код (меняется каждые 30 секунд).
2. Владелец отправляет код агенту в чат.
3. Агент вызывает верификатор — скрипт, защищённый правами root,
   который сверяет код с секретным ключом.
4. Если код правильный — открывается **сессия** (по умолчанию 25
   минут). В пределах сессии агент может выполнять чувствительные
   действия. После — снова просит код.

```
Ты:    удали логи за прошлый месяц
Агент: Это деструктивное действие. Пришли 6-значный код
       из аутентификатора.
Ты:    847291
Агент: Код принят, сессия открыта (25 мин). Удаляю логи...
```

Сессия — это запись с меткой времени в файле на диске, защищённом
правами root. Она говорит: «владелец подтвердил своё присутствие в
момент T». Агент сравнивает T с текущим временем и решает, достаточно
ли свежее подтверждение.

### Два режима использования

**Мягкий режим (источник доверия).** Агент сам проверяет сессию
перед важным действием через MCP-инструменты. Если сессия
просрочена — просит код. Подходит для любой агентской системы,
поддерживающей Model Context Protocol (MCP): Claude Code, Claude
Desktop, Cursor, Continue.

**Жёсткая блокировка (опциональный режим).** Если установлена
интеграция с системой хуков агента, блокировка работает на уровне
операционной системы: агент физически не может вызвать защищённый
инструмент без открытой сессии — даже если вредоносная инъекция в
тексте убедила его это сделать. Поддерживает полную (все инструменты)
и выборочную (только указанные) блокировку.

Можно использовать один режим или оба вместе.

## Быстрый старт для Claude Code

> Требования: `python3` (стандартная библиотека, без pip).
> Опционально: `qrencode` для QR в терминале (`brew install qrencode`
> на macOS, `apt install qrencode` на Linux).
>
> **Подготовь аутентификатор до начала** — шаг 1 покажет QR-код,
> который нужно отсканировать сразу.

```sh
git clone <url-этого-репозитория>
cd totp-presence

# 1. Ядро — секретный ключ + верификатор (покажет QR — сканируй)
sudo ./core/setup.sh install

# 2. Интеграция для Claude Code — хук, файл сессии, конфигурация
sudo ./examples/claude-code-hook/install.sh

# 3. MCP-сервер — инструменты проверки для агента
pip3 install fastmcp  # macOS Homebrew: pip3 install --break-system-packages fastmcp

# 4. Soft-prompt — инструкции агенту когда проверять
# Скопировать блок из examples/soft-prompt/prompt.md в CLAUDE.md
```

**Шаг 1** сгенерирует секретный ключ и покажет QR-код для привязки
аутентификатора. **Шаг 2** создаст файлы интеграции и напечатает
JSON-сниппет для хука — **добавлять сниппет пока не нужно**.

**Шаг 3** — после `pip3 install fastmcp` добавить в `~/.claude.json`:
```json
{
  "mcpServers": {
    "totp-presence": {
      "command": "python3",
      "args": ["<полный-путь>/examples/mcp-server/server.py"]
    }
  }
}
```
Подробности — в [examples/mcp-server/README.ru.md](./examples/mcp-server/README.ru.md).
После добавления — **перезапустить Claude Code**, чтобы MCP-сервер
загрузился.

**Шаги 3-4** дают агенту мягкий режим: он сам проверяет сессию перед
важными действиями и просит код когда нужно.

> **Другие MCP-клиенты** (Claude Desktop, Cursor, Continue): шаг 2
> создаёт файлы сессии, без которых MCP-сервер не работает — он
> нужен даже если хук не активируется. Для остальных клиентов
> достаточно шагов 1, 2, 3, 4 без опционального сниппета.

**Опционально: жёсткая блокировка.** Чтобы агент не мог вызвать
защищённые инструменты без сессии даже при prompt injection — добавь
JSON-сниппет из шага 2 в `~/.claude/settings.json`. Claude Code
попросит подтвердить правку. После этого работают оба режима: агент
проверяет сам через MCP, а хук блокирует на уровне OS.

Перед включением:

- **MCP-сервер должен быть подключён и работать** (шаги 3-4
  завершены, Claude Code перезапущен). Иначе агент не сможет
  вызвать `totp_verify` для открытия сессии — тупик.
- **Если агент работает через Telegram, Slack или другой внешний
  канал** — messaging-инструмент нужно разрешить без сессии, иначе
  агент не сможет ни ответить, ни попросить код. См.
  [claude-code-hook/README.ru.md](./examples/claude-code-hook/README.ru.md),
  секция «Каналы связи».
- **Выборочная блокировка** — альтернатива полной. Защищает только
  указанные инструменты, остальные работают свободно. Меньше
  трения, но новые инструменты не защищены автоматически.

Подробности обоих режимов —
[examples/claude-code-hook/README.ru.md](./examples/claude-code-hook/README.ru.md).

<details>
<summary>macOS + Apple Passwords</summary>

Apple Passwords хранит TOTP-коды только как атрибут существующей
password-записи. Создай запись-плейсхолдер:

1. Passwords → **New Password**
2. Title `totp-presence`, User Name `agent`, Password любой,
   Website `https://totp-presence.local`
3. Сохрани → Codes → **+ → Scan QR Code with Camera** → выбери
   запись `totp-presence`.

Полноценные аутентификаторы (Google Authenticator, Authy, Raivo,
1Password, Bitwarden) плейсхолдер не требуют — просто сканируют QR.

</details>

## Архитектура

Проект разделён на два слоя:

### Ядро (`core/`)

Два скрипта: bash с inline Python на стандартной библиотеке. Ноль
внешних зависимостей. Секретный ключ под правами root, узкое
sudoers-правило (sudo без пароля только для верификатора), одна
публичная команда:

```sh
# Проверить код — да/нет, ничего не меняет
sudo /etc/totp-presence/verify 123456
# exit 0 = код верный, exit 2 = неверный, exit 3 = заблокирован, exit 1 = ошибка

# Проверить код и открыть сессию — записывает метку времени в файл
sudo /etc/totp-presence/verify 123456 \
     --session /etc/totp-presence/claude-code-session
```

Путь для `--session` жёстко валидируется: допускается только файл
внутри `/etc/totp-presence/`. Подробнее — [core/README.ru.md](./core/README.ru.md).

### Интеграции (`examples/`)

Обвязка вокруг ядра, заточенная под конкретную агентскую систему.
Каждая интеграция выбирает имя файла сессии, длину окна и формат
ответа при отказе:

- **[claude-code-hook](./examples/claude-code-hook/)** — хук для
  Claude Code, срабатывающий при каждом вызове инструмента.
  Поддерживает полную и выборочную блокировку, защиту
  конфигурационных файлов укороченным окном (120 секунд) и
  настройку каналов связи для headless-агентов.
- **[mcp-server](./examples/mcp-server/)** — MCP-сервер
  (Model Context Protocol) с тремя инструментами: проверить сессию,
  верифицировать код, показать статус. Работает в любом MCP-клиенте
  (Claude Code, Claude Desktop, Cursor, Continue). Агент сам
  вызывает проверку, когда считает нужным.
- **[soft-prompt](./examples/soft-prompt/)** — текстовые инструкции
  для агента + MCP-инструменты. Промпт говорит агенту *когда*
  проверять (перед опасным действием, при сомнении), MCP даёт *чем*.
  Для систем без поддержки хуков или как дополнение к ним.

Ядро не привязано к конкретной агентской системе. Любой агент,
умеющий вызвать shell-команду, может его использовать.

<details>
<summary>Как написать свою интеграцию</summary>

1. Выбрать имя файла сессии (например,
   `/etc/totp-presence/my-agent-session`).
2. Решить, как долго сессия считается свежей (скользящее окно,
   проверка на каждое действие, и т.п.).
3. В точке проверки читать файл сессии и сравнивать метку времени
   с текущим временем.
4. Когда сессия просрочена — выдать пользователю или агенту
   инструкцию вызвать `verify --session <путь>` со свежим кодом.

Референсный пример —
[claude-code-hook](./examples/claude-code-hook/).

</details>

## Чем это НЕ является

Короткая секция честности. Полная версия —
[SECURITY_MODEL.ru.md](./SECURITY_MODEL.ru.md).

- **Не замена изоляции.** Если атакующий получил root-доступ к
  машине, он может прочитать секретный ключ — защита сломана.
- **Не защита от произвольного кода.** Если агент выполняет shell-
  команды в обход своей штатной системы инструментов, хуки не
  срабатывают.
- **Не универсальный замок.** Защищает только то, на что конкретная
  интеграция повесила проверку.
- **Не подтверждение конкретного действия.** Открытая сессия говорит
  «владелец давал код недавно», а не «владелец одобрил именно это».
- **Не магия.** Принцип Керкгоффса: секретный ключ — единственное,
  что приватно. Код проекта открыт и должен оставаться безопасным
  при этом условии.

## Почему это имеет смысл

Модели становятся лучше в распознавании вредоносных инъекций — но
идентичность отправителя в тексте всё равно не закодирована. Никакое
развитие AI не добавит в обычный текст криптографическую подпись.
Пока агенты принимают команды текстом, им нужен независимый от
канала способ убедиться, кто на другом конце.

Жёсткая блокировка как опциональный слой становится менее критичной
с более способными моделями. Но основная функция — проверяемый сигнал
идентичности — от способностей модели не зависит: это про отсутствие
информации в канале, а не про способность модели распознавать атаки.

При этом добавляя ограничение, ты **расширяешь** то, что можешь
доверить агенту. Без TOTP ты вряд ли разрешишь автономную
GUI-автоматизацию, SSH, работу с паролями — слишком большая зона
риска. С TOTP — разрешишь: для каждого чувствительного шага есть
независимое подтверждение.

## Откуда это взялось

Автор управляет self-hosted мультиагентной системой на Claude Code:
несколько агентов на Mac mini, принимающих команды через
Telegram-ботов. Единственное «доказательство владельца» — привязанный
идентификатор чата. Если Telegram будет угнан, все агенты продолжат
принимать команды как ни в чём не бывало.

В процессе эксплуатации система неоднократно обрабатывала внешние
документы — и стало очевидно, что вредоносная инструкция в тексте
неотличима от команды владельца. Вопрос был не «если», а «когда».

`totp-presence` — ответ до того, как это стало инцидентом: дать
собственным агентам основание считать, что команды приходят от меня.
Этот репозиторий — вынос работающего решения в переиспользуемую форму.

## Prior art

Prior-art поиск (апрель 2026) не нашёл описания этого паттерна
ранее. Смежные работы:

- **Checkmarx Zero, 2025** — «Lies-in-the-Loop / HITL Dialog
  Forging» ставит проблему, говорит «no silver bullet», решения не
  даёт. Этот репозиторий — возможный ответ.
- **1Password + Browserbase, Authn8, open2fa и т.п.** — TOTP в
  *обратном* направлении: агенты доказывают себя сервисам. Здесь —
  наоборот, человек доказывает себя агенту.
