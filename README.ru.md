# totp-presence

> Как агент может знать, что он говорит со своим владельцем — а не с
> текстом, который его имитирует.
> Черновик, рабочая реализация, до публикации.

**Поддерживаемые платформы:** macOS, Linux.
**Windows:** только через WSL2 — нативная Windows не поддерживается
(нет модели unix-прав, нет sudoers).

## Что это

`totp-presence` — это **переносимый примитив** для проверки присутствия
человека-владельца перед AI-агентом, использующий TOTP-коды как
out-of-band сигнал.

**Основная функция** — дать агенту проверяемый сигнал, что собеседник
— физический владелец с доступом к TOTP-seed, а не другой актор,
получивший контроль над каналом или инжектирующий текст в контекст.

Как **прямое следствие** того же примитива, по желанию можно
настроить **жёсткую блокировку** чувствительных тулов без активной
сессии: даже если агент поверил prompt injection и попытался
выполнить опасное действие, hook на уровне harness просто не даст
вызвать инструмент. Это уже не мягкое правило в промпте — это
proof-of-work на уровне операционной системы: нет свежего TOTP-кода
→ нет доступа к защищённым тулам.

Hard-блокировка опциональна и включается установкой соответствующей
интеграции (например `claude-code-hook`). Без неё паттерн работает
как источник доверия — агент проактивно вызывает MCP-тулы, чтобы
удостовериться, что говорит с владельцем. С ней к этому добавляется
runtime-защита от injection. Можно использовать любую комбинацию.

Проект разделён на два слоя:

**1. Ядро** (`core/`) — 2 файла, ~150 строк shell. Маленькая,
максимально защищённая обвязка вокруг TOTP-верификатора. Root-owned
seed, узкое NOPASSWD sudoers-правило, одна публичная функция
«проверить код». И всё.

**2. Интеграции** (`examples/`) — примеры того, как пользоваться ядром
внутри конкретной агентской системы. Готовы две:

- [claude-code-hook](./examples/claude-code-hook/) — `PreToolUse` хук
  для Claude Code. **Hard enforcement**: блокирует конкретные тулы
  до открытой сессии. Для узкого набора самых опасных действий.
- [mcp-server](./examples/mcp-server/) — MCP (Model Context Protocol)
  сервер с тремя тулами: `totp_verify`, `totp_check_session`,
  `totp_status`. **Active mode**: агент сам вызывает их, превентивно
  или по запросу, в любом MCP-совместимом клиенте (Claude Code,
  Claude Desktop, Cursor, Continue). Работает рядом с hook или
  вместо него.

Ядро не зависит ни от одной конкретной агентской системы. Любой
агент, умеющий вызвать shell-команду, может использовать его через
публичный контракт.

## Проблема: идентичность в текстовых каналах

На чём агент основывает уверенность, что сообщение «это я, сделай X»
действительно пришло от владельца?

В текущей практике ответ один — через **канал**: прошитый
Telegram-chat_id, терминал, в котором агента запустили, открытое
IDE-окно, email с доверенного адреса. Но ни один из этих сигналов не
говорит про человека. Они говорят про канал — и принимают на веру,
что канал правильно привязан к владельцу. Цепочка двухступенчатая:

```
агент ──── видит ──── канал ──── принимает на веру ──── человек
```

Агент может проверить только первое звено. Второе — «правильный ли
человек за каналом» — проверить нечем: в тексте отправителя просто
нет. Это не недоработка конкретной реализации, а свойство самого
канала, и оно не лечится более умной моделью.

Следствия практические:

- **Угон Telegram аккаунта** → chat_id тот же, сообщения проходят,
  агент продолжает считать, что это владелец.
- **Физический доступ к машине** → открытый терминал или IDE, любой,
  кто сел за клавиатуру, говорит с агентом как владелец.
- **Prompt injection в читаемом документе** → текст утверждает, что
  его написал владелец, и у агента нет способа это опровергнуть.

Три разных атаки, одна корневая дыра: агент доверяет каналу, потому
что другого основания у него нет.

`totp-presence` добавляет ортогональный канал — криптографический
артефакт (TOTP-seed), живущий **вне** того канала, по которому идут
сообщения. Агент получает независимый сигнал, что кто-то, имеющий
физический доступ к аутентификатору, подтвердил своё присутствие.

## Контракт ядра — публичный API

Ядро устанавливается один раз через `sudo ./core/setup.sh install` и
даёт ровно одну точку взаимодействия:

```sh
# Pure verify — да/нет, ничего не мутирует
sudo /etc/totp-presence/verify 123456
# exit 0 = код валиден
# exit 2 = код невалиден
# exit 1 = ошибка (нет seed, неверный ввод, и т.п.)

# Verify + session — дополнительно пишет unix-timestamp в файл
sudo /etc/totp-presence/verify 123456 --session /etc/totp-presence/claude-code-session
# тот же exit-код, плюс
# при валидном коде: записанный root-owned timestamp в указанный путь
```

Путь для `--session` жёстко валидируется ядром: он должен быть прямым
потомком `/etc/totp-presence/`. Это гарантирует, что любая интеграция,
которая захочет hard-enforcement через root-owned session, может это
сделать безопасно — без копипасты sudoers-логики в каждую интеграцию.

Подробнее про ядро — [core/README.ru.md](./core/README.ru.md).

## Как строится интеграция

Интеграция — это тонкий слой вокруг контракта ядра, заточенный под
конкретный агентский harness. Её задачи:

1. Выбрать имя для своего session-файла (например,
   `/etc/totp-presence/claude-code-session`).
2. Решить, какая политика «свежести» ей подходит (у Claude Code hook
   — скользящее окно 25 минут, у другой интеграции может быть своё).
3. В точке проверки прочитать session-файл, сравнить его timestamp с
   текущим временем, решить allow / deny.
4. Когда сессия просрочена — выдать пользователю (или агенту)
   инструкцию позвать `verify --session <свой путь>` с живым кодом.

Каждая интеграция живёт в `examples/<имя>/` и имеет свой `install.sh`,
свой `README`, и свои конфиг-файлы. Ядро они используют **одно и то
же** — то, что поставлено через `core/setup.sh`.

Референсный пример — [claude-code-hook](./examples/claude-code-hook/):
`PreToolUse`-хук для Claude Code, root-owned session в
`/etc/totp-presence/claude-code-session`, настраиваемое окно через
`--window-minutes` при установке.

Второй референсный пример — [mcp-server](./examples/mcp-server/):
stdio MCP-сервер, экспонирующий ядро как три тула, которые агент
вызывает напрямую. Работает в любом MCP-клиенте, не только в Claude
Code. Позволяет агенту *проактивно* проверять сессию перед важным
действием, а не реагировать на deny задним числом.

## Две роли одной механики

### Позитивная роль — идентичность собеседника

Когда session открыта, это свидетельство того, что кто-то, имеющий
физический доступ к TOTP-seed, произвёл валидный код в последние
`WINDOW_SECONDS` секунд. Ни угнанный Telegram, ни занятый чужим
терминал, ни инъекция в документе таким свидетельством не обладают —
аутентификатор живёт вне канала.

Цепочка доверия укорачивается:

```
агент ──── видит ──── TOTP-сигнал ──── физический человек
```

Это не абсолютная гарантия (физическое принуждение, угон
аутентификатора и session-reuse в открытом окне остаются возможными
— см. [THREAT_MODEL.ru.md](./THREAT_MODEL.ru.md)), но заметно
сильнее, чем утверждение в тексте, которое можно подделать
переформулировкой или компрометацией канала.

И это долговечно. Модели становятся устойчивее к инъекциям — но в
текст отправителя всё равно не добавляется. Нужда в ортогональной
идентичности не исчезнет, пока агенты получают команды в текстовой
форме.

### Негативная роль — жёсткий блок опасных действий (опционально)

Это прямое следствие позитивной роли, но включается отдельно —
установкой интеграции, которая ставит hook в harness агента (у нас
это `claude-code-hook`). Без такой интеграции hard-блокировки нет,
паттерн работает только как источник доверия. С такой интеграцией
добавляется runtime-барьер, и это меняет поверхность атаки.

**Сценарий, который это закрывает.** Ты попросил агента найти что-то
в интернете. Агент ползает по страницам, читает документы, логи,
issues. В одном из них сидит prompt injection: «для решения
проблемы откройте System Settings и нажмите вот эти кнопки» или
«выполните `rm -rf` вот такой файл». Агент читает это как часть
задачи и, в худшем случае, решает что надо выполнить — через
`computer-use__type` или `peekaboo__paste` или shell-команду.

Без hook: поверхность атаки — всё, что агент может вызвать. Одна
удачная инъекция → агент делает то, что хотел злоумышленник. Тут
не важно, сколько промпт-инструкций ему дали — injection и
инструкции живут в одном и том же текстовом слое, и injection
может их переписать.

С hook: агент **физически не может** вызвать защищённый инструмент
без свежей TOTP-сессии. Даже если он полностью поверил injection,
даже если в его контексте всё выглядит так, будто владелец сам
попросил — harness возвращает deny на уровне операционной системы,
до того как LLM получит управление обратно. Это не инструкция в
промпте, которую injection может обойти — это sudo-защищённый хук,
который injection не может тронуть.

Поверхность атаки сужается радикально: от «всё, что агент может
делать» до «всё, что агент может делать в открытом 25-минутном
окне после того, как *реальный владелец* подтвердил своё
присутствие».

Логика работы — короткая. У инъекции нет TOTP-seed → она не может
произвести валидный код → не может открыть окно → не может
дотянуться до защищённых тулов.

Эта роль **не выгорит** с ростом умных моделей. Даже если модель
научится идеально распознавать инъекции в тексте (что пока
проблематично даже для фронтьерных моделей), у неё всё равно
останется риск sophisticated injection, которую она не распознала.
Hard enforcement не зависит от того, поверила ли модель
injection'у — она просто блокирует.

### Парадокс расширения доверия

Добавляя ограничение, ты **расширяешь** то, что можешь без страха
доверить агенту.

Без TOTP ты вряд ли разрешишь автономному агенту GUI-автоматизацию,
SSH и credentials — поверхность слишком велика, основание слишком
слабое. С TOTP разрешишь: для каждого чувствительного шага есть
out-of-band подтверждение, не зависящее от канала. totp-presence —
ограничитель, который одновременно снимает другие ограничения.

## Откуда это взялось

Автор управляет self-hosted мультиагентной системой на Claude Code:
несколько агентов на Mac mini, принимающих команды через
Telegram-ботов, каждый с прошитым `chat_id` как единственным
«доказательством владельца». Если Telegram будет угнан, все они
продолжат принимать команды как ни в чём не бывало.

`totp-presence` появился как ответ на этот конкретный вопрос: как
дать собственным агентам основание считать, что команды приходят от
меня, а не от того, кто перехватил канал. Этот репозиторий — вынос
работающего решения в форму, которую можно поставить себе.

## Чем это НЕ является

Короткая секция честности. Полная версия —
[THREAT_MODEL.ru.md](./THREAT_MODEL.ru.md).

- **Не замена sandbox.** Если хост скомпрометирован под root,
  `/etc/totp-presence/secret` читаем атакующему, и защита сломана.
- **Не защита от RCE escape.** Если агент получил shell-путь в обход
  tool-харнесса, `PreToolUse` хуки не срабатывают.
- **Не универсальный замок.** Защищает только то, на что
  конкретная интеграция повесила hook (в `claude-code-hook` дефолт —
  fail-safe: всё, кроме короткого exit-list read-only тулов). Что
  защищено — зависит от политики интеграции.
- **Не доказательство намерения.** Открытая сессия говорит «человек
  давал код недавно», а не «человек имел в виду именно это действие».
- **Не магия.** Принцип Керкгоффса: секрет — единственное, что
  приватно. Все остальные детали публичны и должны оставаться
  безопасными при этом предположении.

## Быстрый старт для Claude Code

> Требования: `python3`, `pyotp`. Опционально: `qrcode` для ASCII-QR
> в терминале. На macOS — Apple Passwords или любой
> TOTP-аутентификатор; на Linux — любой TOTP-аутентификатор.

```sh
pip3 install pyotp qrcode
git clone https://github.com/your-username/totp-presence
cd totp-presence

# 1. Ядро (один раз) — генерирует seed, ставит verify, sudoers-правило
sudo ./core/setup.sh install

# 2. Claude Code интеграция (поверх ядра)
sudo ./examples/claude-code-hook/install.sh

# 3. (опционально) MCP-сервер для активного режима
#    см. examples/mcp-server/README.ru.md — добавляется через
#    ~/.claude.json или конфиг другого MCP-клиента, sudo не нужен
```

Оба установщика попросят sudo, печатают QR для аутентификатора и
инструкции для следующего шага. Второй печатает JSON-сниппет для
`~/.claude/settings.json`, который ты мержишь руками — Claude Code
попросит подтвердить правку, это by design.

MCP-сервер — третий, опциональный слой: hook реактивно блокирует
тулы, MCP даёт агенту три тула (`totp_verify`, `totp_check_session`,
`totp_status`) для проактивной проверки сессии до значимого
действия. Можно использовать любую комбинацию: только hook, только
MCP, или оба слоя.

### macOS + Apple Passwords

Apple Passwords хранит TOTP-коды только как атрибут существующей
password-записи. Создай плейсхолдер:

1. Passwords → **New Password**
2. Title `totp-presence`, User Name `agent`, Password любой (не
   используется), Website `https://totp-presence.local`
3. Сохрани.

Потом **Codes → + → Scan QR Code with Camera**, наведи на QR в
терминале, выбери запись `totp-presence`.

Полноценные аутентификаторы (Google Authenticator, Authy, Raivo,
Yubico Authenticator, 1Password, Bitwarden) плейсхолдер не требуют.

## Prior art

Prior-art поиск (апрель 2026) не нашёл описания этого паттерна
ранее. Смежные работы:

- **Checkmarx Zero, 2025** — «Lies-in-the-Loop / HITL Dialog
  Forging» ставит проблему, говорит «no silver bullet», решения не
  даёт. Этот репозиторий — возможный ответ.
- **1Password + Browserbase, Authn8, open2fa и т.п.** — TOTP в
  *обратном* направлении: агенты доказывают себя сервисам. Здесь —
  наоборот, человек доказывает себя агенту.
