# claude-code-hook — референсная интеграция для Claude Code

Это пример того, как использовать ядро `totp-presence` внутри Claude
Code через `PreToolUse` хук. Он превращает абстрактный примитив «да /
нет» в жёсткий runtime-блок: защищённые тулы не вызываются, пока
владелец не открыл сессию валидным TOTP-кодом.

## Что устанавливается

Три файла, все принадлежат root и лежат рядом с ядром:

```
/etc/totp-presence/claude-code-guard.sh     root:wheel 755 — PreToolUse хук
/etc/totp-presence/claude-code-session      root:wheel 644 — unix timestamp
/etc/totp-presence/claude-code-config       root:wheel 644 — WINDOW_SECONDS
```

Отдельного sudoers-правила интеграция не добавляет — она использует
существующее ядро-правило для `verify` с флагом `--session`.

## Установка

Ядро должно быть установлено **заранее**:

```sh
sudo ./core/setup.sh install
```

Потом ставишь интеграцию:

```sh
sudo ./examples/claude-code-hook/install.sh
# или с кастомным окном:
sudo ./examples/claude-code-hook/install.sh --window-minutes 15
```

Установщик:

1. Копирует `guard.sh` в `/etc/totp-presence/claude-code-guard.sh`
   (root:wheel 755).
2. Инициализирует `claude-code-session` нулевым таймстемпом (сессия
   сразу «просрочена», нужно явно открыть).
3. Пишет `claude-code-config` с `WINDOW_SECONDS=<N*60>`.
4. Печатает JSON-сниппет для `~/.claude/settings.json`, который надо
   смержить под `hooks.PreToolUse`. Claude Code попросит твоё явное
   подтверждение перед сохранением правки — даже в режиме
   bypass-permissions. Это by design.

## Как агент открывает сессию в runtime

Когда агент пытается вызвать защищённый тул и сессия просрочена,
`guard.sh` возвращает deny с инструкцией. Агент просит TOTP-код у
владельца через свой прямой канал связи и выполняет:

```sh
sudo /etc/totp-presence/verify 123456 --session /etc/totp-presence/claude-code-session
```

Ядро валидирует код, проверяет что путь под `/etc/totp-presence/` (по
протоколу ядра), и пишет текущий unix-timestamp в session-файл под
root. После этого `guard.sh` в следующий раз увидит свежую сессию и
пропустит вызов тула.

## Защищённые тулы — fail-safe дефолт

Дефолтный матчер в `settings.json.snippet` — **`.*`**, то есть **все**
тулы. Каждый tool call приходит в `guard.sh`, и уже сам хук решает,
пускать или требовать сессию.

Внутри `guard.sh` — стабильный, короткий **exit-list** безопасных
read-only тулов, которые пропускаются без проверки:

```
Read | Glob | Grep | LS | TodoWrite | WebSearch
```

Всё, что не в этом списке — требует свежей TOTP-сессии. В том числе:

- `Bash` (shell)
- `Write`, `Edit`, `NotebookEdit` (мутация файлов)
- `WebFetch` (может попасть в action-URL)
- `Task` / `Agent` (запуск подагентов, которые сами могут что-то
  делать)
- Любой MCP-тул (новые плагины/серверы)

Почему такая инверсия. Обычный подход — «перечислить опасные тулы в
матчере» — даёт **fail-open**: всё, что пользователь забыл
перечислить, или что появится в будущем апдейте Claude Code, или что
добавит новый плагин — **не защищено** по умолчанию. Мы же хотим
наоборот: **fail-safe**. Список read-only тулов стабильный, короткий
и редко меняется. Список опасных — большой, нестабильный, и
пользователь не обязан знать всю таксономию, чтобы не облажаться.

**Стоимость:** агент будет чуть чаще сталкиваться с deny на не
read-only действиях. Но только на реальные мутации, а не на чтение
файлов и поиск.

**Как менять политику:** редактировать exit-list в самом верху
`/etc/totp-presence/claude-code-guard.sh` (под sudo, файл root-owned).
Добавлять тул в exit-list стоит, только если он **гарантированно
read-only и agent-local**. Лучше недобавить, чем добавить лишнее.

## Удаление

```sh
sudo ./examples/claude-code-hook/install.sh uninstall
```

Снимает три файла интеграции (guard.sh, session, config). Ядро
(`verify`, `secret`, sudoers для verify) остаётся — его можно
удалить отдельно через `sudo ./core/setup.sh uninstall`.

Матчер в `~/.claude/settings.json` установщик **не** трогает —
печатает точную `jq`-команду, которую ты запускаешь сам. Правка
конфига Claude Code должна оставаться в твоих руках.

## Что этот пример показывает про контракт ядра

Именно эта интеграция демонстрирует, как пользоваться двумя
возможностями ядра:

1. **Pure verify** (без `--session`) — ядро просто говорит да/нет. Эта
   интеграция не использует pure-режим, но мог бы — например,
   для debug-команды, которая проверяет код без открытия сессии.

2. **Verify + write session** (с `--session <path>`) — ядро
   дополнительно пишет unix-timestamp в указанный путь под
   `/etc/totp-presence/`, root-owned. Это то, что используется здесь
   для runtime-блока.

Session-файл и конфиг окна — **зона ответственности этой
интеграции**, не ядра. Если ты пишешь другую интеграцию (Aider,
Cursor, custom bash, REST endpoint) — ты волен либо использовать
тот же паттерн с своим session-файлом, либо вообще не использовать
session, а дёргать verify каждый раз. Ядро одинаково служит обоим.

## Threat model в контексте этой интеграции

См. [../../THREAT_MODEL.ru.md](../../THREAT_MODEL.ru.md) для полной
картины. Кратко про то, что **эта конкретная интеграция** закрывает
и чего нет:

— **Закрывает:** вызов тулов в матчере без свежего TOTP-кода.
Попытку подделать session (файл root-owned). Попытку подменить
guard.sh (файл root-owned).

— **Не закрывает:** тулы не в матчере. Prompt-injection, убеждающую
агента *легитимно* запросить код у владельца под предлогом
безобидной задачи (§4 threat model — session reuse во время
открытого окна). RCE-escape в обход harness.
