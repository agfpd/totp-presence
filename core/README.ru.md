# core — верификационный примитив totp-presence

Это всё, что есть в ядре проекта. Оно делает одну вещь: отвечает на
вопрос «это тот самый TOTP-код от владельца?». Ответ — да или нет.

Всё остальное — session windows, hooks, matchers, интеграции с
конкретными агентскими системами — живёт **вне ядра**, в `examples/`.

## Состав

```
core/
├── setup.sh         — установщик ядра (запускается через sudo)
├── verify.sh        — сам верификатор
└── README.ru.md     — этот файл
```

После установки (`sudo ./core/setup.sh install`) на диске появляется:

```
/etc/totp-presence/
├── secret           root:wheel 600 — base32 TOTP-seed
└── verify           root:wheel 755 — верификатор

/etc/sudoers.d/totp-presence        root:wheel 440 — NOPASSWD для verify
```

Три root-owned артефакта. Всё.

## Публичный API (то, что может вызывать интеграция)

### `sudo /etc/totp-presence/verify <code>`

Чистая функция. Читает seed, сверяет 6-значный код через pyotp,
возвращает exit-код:

- `0` — код валиден
- `2` — код невалиден
- `3` — lockout: слишком много подряд неверных кодов, попробуй позже
- `1` — ошибка (пустой ввод, нет seed, нет pyotp, неверный путь
  `--session`, и т.п.)

На stdout ничего значимого не пишет (одна строка `ok` / `invalid`
для человека).

**Защита от brute force — rate-limit, не жёсткий пол.** После
`MAX_FAILS` подряд неверных кодов (по умолчанию 5) верификатор
блокируется на `LOCKOUT_SECONDS` (по умолчанию 300 = 5 минут).
Счётчик хранится в `/etc/totp-presence/fail-counter` под root и
сбрасывается при первой успешной верификации.

Это эффективно **против серийного атакующего** — ~5 попыток на
каждые 5 минут, ожидаемое время подбора 6-значного кода исчисляется
годами непрерывных вызовов.

**Против параллельного — слабее.** Read–check–verify–write внутри
`verify.sh` не сериализован, поэтому атакующий, форкающий N
конкурентных вызовов через одно NOPASSWD sudoers-правило, читает
один и тот же pre-check counter N раз и проходит проверку лимита N
раз за раунд. При N≈100 форков на раунд и `valid_window=1`
ожидаемое время подбора падает примерно до двух недель непрерывного
brute-force. Две недели всё ещё слишком медленно для реалистичного
injection-сценария, но это не «годы» как жёсткий пол. Если threat
model требует именно жёсткого пола — оберни verify во внешний
`flock` или добавь блокировку вокруг критической секции в скрипте.
Подробнее — в [../THREAT_MODEL.ru.md](../THREAT_MODEL.ru.md).

### `sudo /etc/totp-presence/verify <code> --session <path>`

То же самое, но при валидном коде **дополнительно** пишет текущий
unix-timestamp в `<path>`. Этот path жёстко валидируется ядром:

- должен быть абсолютным путём внутри `/etc/totp-presence/`
- должен быть прямым потомком каталога (никаких подкаталогов)
- никаких `..`, никаких `//`

После записи файл становится `root:wheel 644`.

Это единственный способ для интеграций безопасно хранить session.
Путь и имя выбирает интеграция, например:

```sh
sudo /etc/totp-presence/verify 123456 \
     --session /etc/totp-presence/claude-code-session
```

## Что ядро НЕ делает

- Не знает про окна (`WINDOW_SECONDS`).
- Не знает про harness-и (Claude Code, Aider, Cursor, свой bash).
- Не знает про форматы deny-ответов (JSON, HTTP, exception).
- Не знает, где агент берёт код (Telegram, stdin, web-UI).
- Не редактирует `~/.claude/settings.json` или любые другие
  user-уровневые конфиги.
- Не предоставляет отдельную команду «проверить, открыта ли сессия
  прямо сейчас» — это делает интеграция, просто читая свой
  session-файл и сравнивая с текущим временем.

Если тебе кажется, что ядро должно что-то из этого уметь —
скорее всего, это логика интеграции, и ей место в `examples/`.

## Минимальный smoke-тест после установки

```sh
# 1. Pure verify — только да/нет, состояние не трогается
sudo /etc/totp-presence/verify 123456   # подставь свежий код
echo $?                                  # 0 = ok, 2 = invalid

# 2. Verify + session — открывает сессию в своём файле
sudo /etc/totp-presence/verify 123456 \
     --session /etc/totp-presence/test-session
ls -l /etc/totp-presence/test-session    # root:wheel 644
cat /etc/totp-presence/test-session      # unix timestamp

# чистим
sudo rm /etc/totp-presence/test-session
```

## Если хочешь написать свою интеграцию

Минимум, что тебе понадобится:

1. Выбрать имя session-файла внутри `/etc/totp-presence/`, например
   `my-integration-session`.
2. При каждой точке проверки в твоей интеграции читать этот файл и
   сравнивать unix-timestamp с текущим временем минус `WINDOW_SECONDS`.
3. Когда сессия просрочена — выдавать пользователю (или агенту)
   инструкцию выполнить:
   ```sh
   sudo /etc/totp-presence/verify <code> --session /etc/totp-presence/my-integration-session
   ```
4. Всё. Ядро сделает остальное.

Реальный пример — [../examples/claude-code-hook/](../examples/claude-code-hook/).

## Почему так мало

Меньше кода — меньше поверхность аудита. Меньше состояния — меньше
способов ошибиться. Меньше решений в ядре — больше свободы у
интеграций. Это не аскетизм, это архитектурный принцип: ядро делает
одно, делает это хорошо, остальное — дело вызывающего.

Если ядро сделано правильно, его можно прочитать за пять минут,
понять за десять, и не сомневаться в нём после. Именно это и есть
точка, в которой вся security-часть проекта держится на плаву.
