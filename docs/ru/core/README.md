# core — верификационный примитив totp-presence

Ядро проекта. Делает одну вещь: отвечает на вопрос «это правильный
6-значный TOTP-код от владельца?». Ответ — да или нет.

Всё остальное — окна сессий, хуки, интеграции с конкретными
агентскими системами — живёт **вне ядра**, в `examples/`.

## Состав

```
core/
├── setup.sh         — установщик ядра (запускается через sudo)
├── verify.sh        — верификатор
└── README.md     — этот файл
```

После установки (`sudo ./core/setup.sh install`) на диске появляется:

```
/etc/totp-presence/                    статика, sysadmin-managed
├── secret                             root:wheel 600 — секретный ключ (base32)
├── verify                             root:wheel 755 — верификатор
└── VERSION                            root:wheel 644 — маркер установленной версии

/etc/sudoers.d/totp-presence           root:wheel 440 — sudo без пароля для verify
```

Четыре артефакта под root. Это вся статическая инсталляция.

При работе создаётся временное дерево состояния (tmpfs на Linux,
синтетическая ФС на macOS — очищается при перезагрузке):

```
/var/run/totp-presence/                root:wheel 755 — корень состояния
├── fail-counter                       root:wheel 644 — счётчик неудач (общий)
├── .verify-lock/                      root:wheel     — блокировка параллелизма (общая)
└── <пользователь>/                    root:wheel 755 — пространство имён по пользователю
    └── <интеграция>-session           root:wheel 644 — метка сессии (по интеграции)
```

Общие на машину для блокировки и счётчика (один секрет → одно общее
ограничение частоты), отдельные для каждого пользователя для сессий
(каждый пользователь держит свой сигнал присутствия). Перезагрузка
очищает все временные файлы; после перезагрузки пользователь должен
заново аутентифицироваться. Это намеренно: «владелец был у машины
N минут назад» не должно переживать выключение питания.

## Обновление

После `git pull` на более новую версию запускай команду
обновления, а не `install` заново:

```sh
sudo ./core/setup.sh update
```

`update` заменяет `/etc/totp-presence/verify` и
`/etc/totp-presence/VERSION` копиями из исходного дерева и
очищает счётчик неудачных попыток, чтобы обновлённый
верификатор стартовал с чистого состояния. Секретный ключ
(`/etc/totp-presence/secret`), правило sudoers, привязки
аутентификаторов и файлы сессий всех интеграций остаются
нетронутыми. Повторная привязка не нужна.

Если установлены интеграции, у каждой обычно есть собственная
подкоманда `update` — смотри README интеграции
(например, [`examples/claude-code-hook/README.md`](../examples/claude-code-hook/README.md)).

Команда `install` не подходит для обновления: она спрашивает,
переписать ли секретный ключ (неверный ответ либо сломает
привязку аутентификатора, либо прервёт установку), печатает
новый `otpauth://`-URL и QR-код и запускает self-test, который
ждёт ввода свежего кода от человека. `update` всё это пропускает.

## Публичный API

### `sudo /etc/totp-presence/verify <код>`

Чистая проверка. Читает секретный ключ, сверяет 6-значный код
(HMAC-SHA1, RFC 6238), возвращает код завершения:

- `0` — код верный
- `2` — код неверный (счётчик промахов увеличен)
- `3` — заблокирован. Либо счётчик достиг `MAX_FAILS` подряд неверных
  попыток в пределах окна `LOCKOUT_SECONDS`, либо счётчик не удалось
  сохранить на диск в этой попытке (отказ в сторону безопасности:
  блокирует перебор через принудительные сбои записи). Сообщение на
  stderr позволяет различить эти два случая.
- `1` — ошибка без изменения счётчика: пустой ввод, нет ключа или
  он в неверном формате, нет python3, неверный путь `--session`,
  сбой записи файла сессии, сбой интерпретатора python3 или
  неожиданный вывод python3.

Вывод: при успехе — `ok` на stdout. При ошибке — сообщение на
**stderr** (не stdout). Это важно для скриптования: stdout чист при
любом исходе кроме успеха.

**Защита от перебора.** После 5 подряд неверных кодов верификатор
блокируется на 5 минут. Успешная проверка сбрасывает счётчик.
Параллельные вызовы сериализуются через исключительную блокировку
(атомарный mkdir), так что параллельный атакующий не обходит счётчик.

Если верификатор был принудительно завершён в процессе работы
(SIGKILL, нехватка памяти), каталог блокировки остаётся и иначе
блокировал бы все последующие проверки на полный 30-секундный
тайм-аут. Верификатор автоматически переиспользует блокировку,
которая существует дольше ~60 с — `sudo rmdir` для этого случая
больше не нужен. Живой verify, успевший взять блокировку в этот
момент, по-прежнему её держит.

### `sudo /etc/totp-presence/verify <код> --session <путь>`

То же самое, но при верном коде **дополнительно** записывает текущую
метку времени (unix timestamp) в указанный файл. Путь жёстко
валидируется:

- должен быть внутри `/var/run/totp-presence/<вызывающий-пользователь>/`
  (где `<вызывающий-пользователь>` берётся из `SUDO_USER` — запуск
  verify под root напрямую отвергается)
- должен быть прямым потомком этой пользовательской директории (без
  подкаталогов)
- без `..`, без `//`
- имя файла должно оканчиваться на `-session` (чтобы вызывающий не
  мог перенаправить запись на состояние соседней интеграции или на
  что-либо ещё во временном дереве)
- не должен быть символической ссылкой

Пользовательская директория создаётся верификатором по требованию
при первом успешном коде — `install.sh` интеграции её не создаёт.

Сама запись атомарная и устойчивая к символическим ссылкам: содержимое
сначала пишется в соседний временный файл (`mktemp` в той же
директории), права и владелец проставляются на временном файле, затем
`mv -f` ставит его на место. Никакого промежуточного состояния не
видно снаружи.

После подстановки файл — `root:wheel 644`.

Это единственный способ для интеграций безопасно хранить сессию.
Путь и имя выбирает интеграция:

```sh
sudo /etc/totp-presence/verify 123456 \
     --session /var/run/totp-presence/$USER/claude-code-session
```

## Что ядро НЕ делает

- Не знает про окна сессии и их длительность.
- Не знает про конкретные агентские системы и их интерфейсы.
- Не редактирует пользовательские конфигурации
  (`~/.claude/settings.json` и т.п.).
- Не предоставляет команду «проверить, открыта ли сессия» — это
  делает интеграция, читая свой файл сессии и сравнивая метку
  времени с текущим моментом.

Если кажется, что ядро должно что-то из этого уметь — скорее всего,
это логика интеграции, и ей место в `examples/`.

## Проверка после установки

```sh
# 1. Чистая проверка — только да/нет, ничего не меняет
sudo /etc/totp-presence/verify 123456   # подставь свежий код
echo $?                                  # 0 = верный, 2 = неверный

# 2. Проверка + сессия — записывает метку времени в файл
sudo /etc/totp-presence/verify 123456 \
     --session /var/run/totp-presence/$USER/test-session
ls -l /var/run/totp-presence/$USER/test-session    # root:wheel 644
cat /var/run/totp-presence/$USER/test-session      # unix timestamp

# чистим
sudo rm /var/run/totp-presence/$USER/test-session
```

## Как написать свою интеграцию

Минимум:

1. Выбрать имя файла сессии. Путь должен оканчиваться на `-session`
   и лежать в per-user runtime-директории, например
   `/var/run/totp-presence/<user>/my-integration-session`. Верификатор
   создаст директорию по требованию при первом успешном коде.
2. При каждой точке проверки читать этот файл и сравнивать метку
   времени с текущим временем минус длительность окна.
3. Когда сессия просрочена — выдать пользователю или агенту
   инструкцию выполнить:
   ```sh
   sudo /etc/totp-presence/verify <код> --session /var/run/totp-presence/$USER/my-integration-session
   ```
4. Всё. Ядро сделает остальное.

Реальный пример — [../examples/claude-code-hook/](../examples/claude-code-hook/).
