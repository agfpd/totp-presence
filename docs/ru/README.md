# totp-presence

*Сигнал присутствия владельца для AI-агентов через TOTP.*

С этим сигналом агенту можно доверить SSH, автоматизацию
графического интерфейса, управление паролями — действия, чья зона
риска слишком велика без подтверждения присутствия человека на
каждом шаге.

> Как агент может знать, что он говорит со своим владельцем — а не с текстом,
> который его имитирует?

**Платформы:** macOS — рабочая. Linux — код переносимый, но не
проверен на живых системах. Windows — только через WSL.

## Проблема: идентичность в текстовых каналах

На чём агент основывает уверенность, что сообщение «это я, сделай X»
действительно пришло от владельца?

На практике — через **канал**: привязанный Telegram-аккаунт, терминал,
IDE-окно, email с доверенного адреса. Но ни один из этих сигналов не
говорит про человека. Они говорят про канал — и принимают на веру, что
за каналом сидит именно владелец:

```
агент --[проверяемо]--> канал --[на веру]--> человек
```

Агент может проверить первое звено: «канал тот самый». Второе —
«правильный ли человек за каналом» — проверить нечем: в тексте этой
информации нет. Это не недоработка, а свойство текстового канала, и
оно не лечится более способной моделью.

Три разных атаки — одна корневая дыра:

- **Угон Telegram** → идентификатор чата тот же, агент продолжает
  слушаться.
- **Физический доступ к машине** → открытый терминал = полный контроль.
- **Prompt injection** → вредоносный текст в документе утверждает, что
  его написал владелец, и агент не может это опровергнуть.

Во всех случаях агент доверяет каналу, потому что другого основания
у него нет.

## Почему встроенного Allow / Deny недостаточно

Агентские системы вроде Claude Code уже спрашивают «Allow / Deny»
перед чувствительными действиями. Разве этого не хватает?

Запрос подтверждения проверяет, что **кто-то** сидит за клавиатурой.
Он не проверяет **кто**. Открытый терминал, угнанная SSH-сессия,
коллега, ребёнок — любой, у кого есть физический или удалённый доступ
к сессии, может нажать Allow.

Это та же проблема доверия каналу: запрос верит каналу («за этим
терминалом сидит человек») и принимает на веру, что это владелец.

Три дополнительных сценария, где запрос подтверждения вообще не
работает:

- **Автономные агенты без терминала** — запущенные через `--agent`,
  `launchd`, `cron` или непрерывную интеграцию. Терминала нет,
  нажимать Allow некому. Инструменты выполняются без подтверждения.
- **Инструменты в списке разрешённых** — когда пользователь отказался
  от подтверждений для часто используемых инструментов (Bash, Write,
  Edit). После этого они работают без спроса — в том числе под
  инъекцией.
- **Не-Claude-Code клиенты** — Cursor, Continue, Claude Desktop и
  другие MCP-клиенты могут иметь другую модель подтверждений или не
  иметь её вовсе.

## Решение

`totp-presence` добавляет второй, независимый канал проверки —
секретный ключ, который живёт **вне** канала связи: в аутентификаторе
на телефоне владельца (Google Authenticator, Apple Passwords, 1Password,
Authy и т.п.).

```
агент --[проверяемо]--> TOTP-сигнал --> физический человек
```

Ключевое свойство: **инъекция не знает секретного ключа** — и всё
остальное за ней рушится. Без ключа нет валидного кода. Без кода —
сессии. Без сессии — защищённых действий.

### Как это выглядит на практике

1. Владелец открывает аутентификатор на телефоне и видит 6-значный
   код (меняется каждые 30 секунд).
2. Владелец отправляет код агенту в чат.
3. Агент вызывает верификатор — скрипт, защищённый правами root,
   который сверяет код с секретным ключом.
4. Если код правильный — открывается **сессия** (по умолчанию 25
   минут). В пределах сессии агент может выполнять чувствительные
   действия. После — снова просит код.

```
Ты:    удали логи за прошлый месяц
Агент: Это деструктивное действие. Пришли 6-значный код
       из аутентификатора.
Ты:    847291
Агент: Код принят, сессия открыта (25 мин). Удаляю логи...
```

Сессия — это запись с меткой времени в файле на диске, защищённом
правами root. Она говорит: «владелец подтвердил своё присутствие в
момент T». Агент сравнивает T с текущим временем и решает, достаточно
ли свежее подтверждение.

> **Важное ограничение:** открытая сессия подтверждает *присутствие*,
> а не *согласие на конкретное действие*. Если сессия открыта на 25
> минут, любое действие внутри этого окна пройдёт без нового кода —
> включая действия, запущенные инъекцией. Меры: держать окно коротким,
> использовать встроенную защиту конфигов (окно 120 с) и добавить
> промпт-правила для необратимых действий. Полный анализ —
> [SECURITY_MODEL.md, §3](./SECURITY_MODEL.md#3-переиспользование-сессии--не-подтверждение-конкретного-действия).

### Два режима использования

**Мягкий режим (источник доверия).** Агент сам проверяет сессию
перед важным действием через MCP-инструменты. Если сессия
просрочена — просит код. Подходит для любой агентской системы,
поддерживающей Model Context Protocol (MCP): Claude Code, Claude
Desktop, Cursor, Continue.

**Жёсткая блокировка (опциональный режим).** Если установлена
интеграция с системой хуков агента, блокировка работает на уровне
операционной системы: агент физически не может вызвать защищённый
инструмент без открытой сессии — даже если вредоносная инъекция в
тексте убедила его это сделать. Поддерживает полную (все инструменты)
и выборочную (только указанные) блокировку.

Можно использовать один режим или оба вместе.

## Быстрый старт для Claude Code

> Требования: `bash 3.2+` (стандартный `/bin/bash` на macOS — 3.2.57,
> поддерживается; дистрибутивы Linux идут с 4 или 5), `python3`
> (стандартная библиотека, без pip).
> Опционально: `qrencode` для QR в терминале (`brew install qrencode`
> на macOS, `apt install qrencode` на Linux).
>
> **Подготовь аутентификатор до начала** — шаг 1 покажет QR-код,
> который нужно отсканировать сразу.

```sh
git clone https://github.com/agfpd/totp-presence.git
cd totp-presence

# 1. Ядро — секретный ключ + верификатор (покажет QR — сканируй)
sudo ./core/setup.sh install

# 2. Интеграция для Claude Code — хук, файл сессии, конфигурация
sudo ./examples/claude-code-hook/install.sh

# 3. MCP-сервер — инструменты проверки для агента
pip3 install fastmcp  # macOS Homebrew: pip3 install --break-system-packages fastmcp

# 4. Soft-prompt — инструкции агенту когда проверять
# Скопировать блок из examples/soft-prompt/prompt.md в CLAUDE.md.
# Обязательно: блок содержит timing-правило — totp_verify должен
# быть первым tool-call в turn'е, когда приходит код. Коды живут
# ~30с, промежуточные рассуждения съедают окно. Это правило должно
# оставаться в любом сценарии, не вырезай его.
```

**Шаг 1** сгенерирует секретный ключ и покажет QR-код для привязки
аутентификатора. **Шаг 2** создаст файлы интеграции и напечатает
JSON-фрагмент для hook — **добавлять фрагмент пока не нужно**.

**Шаг 3** — после `pip3 install fastmcp` добавить в `~/.claude.json`:
```json
{
  "mcpServers": {
    "totp-presence": {
      "command": "python3",
      "args": ["/абсолютный/путь/до/examples/mcp-server/server.py"]
    }
  }
}
```
Подробности — в [examples/mcp-server/README.md](./examples/mcp-server/README.md).
После добавления — **перезапустить Claude Code**, чтобы MCP-сервер
загрузился.

**Шаги 3-4** дают агенту мягкий режим: он сам проверяет сессию перед
важными действиями и просит код когда нужно.

> **Другие MCP-клиенты** (Claude Desktop, Cursor, Continue): шаг 2
> создаёт файлы сессии, без которых MCP-сервер не работает — он
> нужен, даже если hook не активируется. Для остальных клиентов
> достаточно шагов 1, 2, 3, 4 без опционального фрагмента.

**Опционально: жёсткая блокировка.** Чтобы агент не мог вызвать
защищённые инструменты без сессии даже при инъекции в промпт —
добавьте JSON-фрагмент из шага 2 в `~/.claude/settings.json`.
Claude Code попросит подтвердить правку. После этого работают оба
режима: агент проверяет сам через MCP, а hook блокирует на уровне
операционной системы.

Перед включением:

- **MCP-сервер должен быть подключён и работать** (шаги 3-4
  завершены, Claude Code перезапущен). Иначе агент не сможет
  вызвать `totp_verify` для открытия сессии — взаимная блокировка.
- **Если агент работает через Telegram, Slack или другой внешний
  канал** — инструмент обмена сообщениями нужно разрешить без сессии,
  иначе агент не сможет ни ответить, ни попросить код. См.
  [claude-code-hook/README.md](./examples/claude-code-hook/README.md),
  раздел «Каналы связи».
- **Выборочная блокировка** — альтернатива полной. Защищает только
  указанные инструменты, остальные работают свободно. Меньше
  трения, но новые инструменты не защищены автоматически.

Подробности обоих режимов —
[examples/claude-code-hook/README.md](./examples/claude-code-hook/README.md).

## Обновление

После `git pull` — путь обновления. Ни одна из команд не трогает
секретный ключ, правило sudoers, привязку аутентификатора и
конфигурационные файлы: открытые сессии остаются открытыми,
привязанные аутентификаторы — валидными.

```sh
cd totp-presence
git pull
sudo ./core/setup.sh update
sudo ./examples/claude-code-hook/install.sh update   # для каждой установленной интеграции
```

- `core/setup.sh update` — заменяет `verify` и
  `/etc/totp-presence/VERSION`, сбрасывает счётчик неудачных попыток
  (чтобы обновлённый верификатор стартовал с чистого состояния),
  сохраняет секретный ключ и правило sudoers.
- `claude-code-hook/install.sh update` — заменяет
  `claude-code-guard.sh`, сохраняет `claude-code-config` (значения
  `WINDOW_SECONDS`, `EXTRA_SAFE_TOOLS`, `EDIT_WRITE_CONFIG_ONLY`
  остаются прежними) и файл сессии данного пользователя. Claude Code
  подхватит новый guard при следующем вызове инструмента —
  перезапуск не нужен.

Чтобы изменить окно сессии или список разрешённых инструментов
обмена сообщениями — запустите `install` повторно с соответствующими
флагами (повторная установка безопасна: неуказанные флаги сохраняют
существующие значения конфигурации).

## Архитектура

Два слоя:

- **Ядро (`core/`).** Bash + Python (только стандартная библиотека),
  ни одной внешней зависимости. Секретный ключ хранится под root,
  узкое правило sudoers даёт беспарольный sudo только верификатору,
  одна публичная команда (`verify <код> [--session <путь>]`) делает
  всё. Размещение по FHS: статические файлы — под
  `/etc/totp-presence/`, состояние времени выполнения (сессии,
  счётчик переборов, блокировка) — под `/var/run/totp-presence/`,
  отдельно по пользователю, очищается при перезагрузке. API, коды
  возврата, валидация пути — [core/README.md](./core/README.md).

- **Интеграции (`examples/`).** Готовые к работе референсные
  интеграции, не демонстрационные. Каждая оборачивает ядро под
  конкретную агентскую систему, выбирая имя файла сессии, длину окна
  и формат ответа при отказе:
  - [claude-code-hook](./examples/claude-code-hook/) — `PreToolUse`
    hook для Claude Code. Полная и выборочная блокировки, укороченное
    120-секундное окно для конфигурационных файлов, список
    разрешённых инструментов обмена сообщениями для агентов без
    терминала.
  - [mcp-server](./examples/mcp-server/) — MCP-сервер с тремя
    инструментами (проверить сессию, верифицировать код, статус).
    Работает в любом MCP-клиенте.
  - [soft-prompt](./examples/soft-prompt/) — инструкции агенту плюс
    MCP-инструменты. Для клиентов без поддержки hook или как
    дополнение.

Ядро не привязано к конкретной агентской системе — им может
пользоваться любой процесс, умеющий вызвать shell-команду. Как
написать свою интеграцию —
[core/README.md](./core/README.md#как-написать-свою-интеграцию).

## Почему это имеет смысл

Идентичность отправителя в тексте не закодирована, и никакое
улучшение модели не добавит в обычный текст криптографическую
подпись. Пока агенты принимают команды текстом, им нужен независимый
от канала способ убедиться, кто на другом конце. Жёсткая блокировка
как опциональный слой становится менее критичной с более способными
моделями, но основная функция — проверяемый сигнал идентичности — от
способностей модели не зависит: это про отсутствие информации в
канале, а не про способность модели распознавать атаки.

## Откуда это взялось

Я делал автономных агентов в Telegram, единственным доказательством
владельца у них был привязанный chat_id — и я к этому привык как к
должному. Всё изменилось, когда я дал агенту доступ к графическому
интерфейсу. Подтверждать системные диалоги, нажимать по чужим
окнам, делать на компьютере всё что угодно — это же теперь мог
сделать и сам агент. Меня это испугало. Но и жёстко ограничивать не
хотелось — постоянно подтверждать каждый шаг ломает саму идею
автономности.

Тогда и родилась идея окна: агент получает доступ к опасным
инструментам только тогда, когда я это подтверждаю присутствием.
Не постоянный Allow/Deny (который не доказывает идентичность), а
временной слот. Вне окна — недоступно, внутри — работай.

Агенты у меня читали сайты, внешние документы — и стало очевидно:
вредоносная инструкция в тексте неотличима от команды владельца.
Агент не видит разницы, потому что её там нет.
